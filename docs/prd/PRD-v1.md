## 一、产品定位

**一句话描述**：AutoWrite 是一款本地优先的 AI 辅助长篇小说创作桌面应用，通过三步大纲生成流水线、逐章流式写作配合三层叙事记忆系统，让用户从"设定参数"到"完整小说"全程自动化，同时保留本地数据所有权和离线创作能力。

**目标用户**：
- **主要用户**：网文/轻小说创作者（25-40岁），有创作意愿但受限于时间和文笔，希望用 AI 提升产出效率。技术水平中等，熟悉各类 AI 工具但不满于通用 ChatGPT 的"记忆断层"问题。
- **次要用户**：全职/兼职网文作者，已有写作能力，用 AI 辅助突破瓶颈和维持日更节奏。

---

## 二、问题陈述

网文创作者在使用通用 AI（ChatGPT/DeepSeek）写长篇小说时，遇到一个结构性问题：**记忆断层**。AI 的上下文窗口无法容纳整部小说，写到第 5-10 章后，AI 开始忘记前面的角色设定、剧情伏笔和世界规则。

**现有方案不足**：
1. 通用 AI 对话：手动维护角色卡/世界观文档，手动、费时
2. 云端 AI 写作工具（NovelAI/Sudowrite）：Story Bible 是被动参考，且按月订阅成本高
3. 国内 AI 写作平台：功能泛化，缺少专业长篇创作流程

**AutoWrite 的差异化**：三层叙事记忆系统（主动事实注入）正是行业研究认为唯一有效的"主动事实注入"方案。但当前实现存在工程债务，本次重构目标是消除技术债务，为后续功能迭代打下基础。

2. Story Bible 是被动的——AI 不被强制使用
3. 滚动摘要丢失细节
4. 文风漂移——越长越平庸
5. 订阅成本长期累积高

## 四、我们的差异化

1. **主动记忆注入 > 被动 Story Bible**：每章生成后自动提取结构化事实，自动注入下一章 Prompt
2. **本地优先 + 数据所有权**：桌面应用，所有数据本地存储，无订阅费，Ollama 可完全离线
3. **双 Provider 灵活切换**：OpenAI 兼容 API + Ollama 本地模型
4. **三步大纲流水线 + 流式预览**：世界观 → 角色 → 章节大纲，每步流式预览
5. **一体化图片生成**：封面、角色立绘、场景插图三类配图

## 六、核心用户流程（重构后）

1. **初始化**：选择本地目录 → 配置AI模型 → 创建小说
2. **大纲生成**（三步流水线）：世界观 → 角色 → 章节大纲，每步可单独重新生成
3. **逐章创作**（核心循环）：AI根据大纲+三层记忆流式生成 → 自动记忆提取 → 注入下一章
4. **配图生成**：封面 → 角色立绘 → 场景插图（AI从章节提取场景描述）
5. **多格式导出**：Markdown / 纯文本 / Word文档 / PDF

## 九、验收标准（Given/When/Then 摘要）

**大纲三步生成**
- Given 用户已创建小说并配置了有效的AI Provider
- When 用户点击"生成大纲"并选择"世界观"步骤
- Then 流式预览区逐步显示世界观文本，完成后世界观保存到novel.yaml

**逐章流式生成**
- Given 大纲已生成且当前章节数<目标章节数
- When 用户点击"写下一章"
- Then 章节正文流式渲染到预览区，完成后文件保存为001-标题.md，三层记忆自动更新

**三层记忆更新**
- Given 一章正文生成完成
- When 记忆提取流程执行
- Then context.yaml中character_states/plot_events/unresolved_threads/emotional_arc/current_intent均更新

**图片生成**
- Given 用户已配置ModelScope API Token
- When 用户在场景插图页选择章节并点击"AI提取场景"
- Then AI从章节正文提取场景描述，用户确认后生成图片并保存

**多格式导出**
- Given 小说已有至少1章正文
- When 用户选择导出格式并点击导出
- Then 系统弹出保存对话框，文件写入成功（MD/TXT后端生成，DOCX前端生成，PDF打印视图）

**错误处理**
- Given AI Provider不可达
- When 用户触发任何AI生成操作
- Then 显示明确的错误分类，提供重试按钮和降级方案提示

## 十二、现有代码痛点清单

1. **Chapters.tsx模块级状态hack**：使用模块级genState对象，极脆弱，需用Zustand替代
2. **Outline.tsx轮询机制**：使用setInterval每1秒轮询，应改用纯Tauri事件监听
3. **appSlice.ts Redux过度复杂**：单一slice+6个asyncThunk，Zustand可大幅简化
4. **App.tsx内联主题配置**：40行Ant Design ConfigProvider，迁移到Tailwind/shadcn设计令牌
5. **后端state.rs**：需确认state模块完整性
6. **后端commands层薄壳**：novel.rs command只是简单转发，可考虑重新分层
7. **memory.rs的parse_json_response**：用正则提取JSON，对模型输出格式依赖强
8. **image.rs的content[:3000]截断**：按字节截断可能导致UTF-8字符断裂，应按字符截断
