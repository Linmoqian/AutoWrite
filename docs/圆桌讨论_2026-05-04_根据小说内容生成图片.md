# 圆桌讨论：根据小说内容生成图片（API和本地）

> 日期：2026-05-04
> 参与角色：架构师、设计师、编程手、体验者、恶魔、苏格拉底
> 讨论轮次：3

## 主持人开场

今天讨论的核心问题：在 AI 小说创作应用中，如何根据小说内容自动生成配图？这涉及两条截然不同的技术路线——调用云端 API（如 DALL-E、Stable Diffusion API、Flux 等）vs 本地部署模型（如 Ollama 配合 SD WebUI、ComfyUI）。关键张力在于：云端 API 上手快但成本不可控、隐私风险高；本地模型灵活但硬件门槛高、质量参差不齐。此外，"从小说文本到高质量图片"这条链路本身存在 Prompt 工程难题——如何从章节内容提取视觉关键词、如何保持角色/场景的一致性、如何匹配小说的整体美学风格，都是需要深入讨论的问题。

---

## 第一轮：各抒己见

### 架构师

核心观点：双轨并行，抽象层屏蔽差异。从架构上看，这个问题和现有的 AI Provider 设计（OpenAI + Ollama 双轨）是完全同构的问题。应该定义一个 `ImageProvider` trait，让 API 和本地部署成为可互换的实现。用户群体是分层的——写短篇的休闲用户硬件跑不动本地 SD，严肃长篇作者几百章下来云端成本可能超过 100 美元。

架构上最关键的设计点是中间层——文本到 Prompt 的转换引擎。这是整条链路中与 Provider 无关的部分：章节内容 -> 视觉元素提取 -> 结构化 Prompt。建议做成独立的 Rust 模块，内部包含角色外貌一致性管理、场景关键词提取、风格模板系统三个子模块。

本地只支持固定几套预设工作流（封面、角色立绘、场景插图），不做自定义编排。一致性是最大的架构挑战——需要独立的角色视觉档案系统：首次生成时提取角色外貌描述并固化，后续章节引用这个档案作为 Prompt 的固定前缀。

### 设计师

核心观点：图片生成的核心问题不是技术路线，而是美学一致性。无论选 API 还是本地模型，如果不能解决"视觉风格统一"这个根本问题，用什么方案都是白搭。

三个主张：第一，配图必须服务于叙事节奏，不能喧宾夺主，需要一个"视觉节奏引擎"智能决策在哪里生成图片、生成什么尺幅。第二，角色视觉一致性是硬性要求，需要用户确认的"角色参考图"作为视觉锚点。第三，倾向本地优先、API 兜底的混合策略——"墨夜书房"的东方水墨风格通过本地 LoRA 微调能做到高度定制，但 API 很难脱离平台审美。

最后强调：需要一个**视觉语义翻译层**，把文学性描述转化为具体的构图、光影、色调指令。这是设计工作，不是工程工作。宁可出图慢一点、少一点，也不能让一张风格违和的图片打断读者的沉浸感。

### 编程手

核心观点：先做 API 路线，本地模型作为可选插件，不要试图抽象出一个"统一接口"。云端 API（DALL-E、Flux 等）本质是 HTTP 请求，5 分钟就能跑通。但本地模型（SD WebUI、ComfyUI）的调用方式完全不同——服务是否启动、模型是否加载、显存够不够。两者的错误类型、超时策略、重试逻辑完全不一样。

DALL-E 3 返回 URL，Flux 返回 base64，SD WebUI 返回 PNG 二进制流。强行抽象一个 `ImageProvider` trait，结果就是接口膨胀成万能字典，类型安全全丢。

真正的工程难点是从小说章节文本到图片 prompt 的"翻译"——这本身就需要一次 LLM 调用。这个提取逻辑比调 API 复杂得多，而且跟图片生成服务无关。建议：第一步先跑通"章节文本 -> LLM 提取视觉描述 -> 调用 DALL-E 生成图片"这条链路，第二步把图片生成调用点抽成函数。不要一上来就搞 provider 抽象层。

### 体验者

核心观点：用户不关心技术路线，用户只关心"点一下就能看到配图"。大多数用户第一次尝试"AI 配图"时，期待的是 Kindle 出版物的水平，但实际得到的是幼儿园涂鸦。这个期望落差才是首要问题。

默认体验必须是零配置可用的。如果需要用户理解"Stable Diffusion""ComfyUI""显存要求""模型下载"这些概念，这个功能对 80% 的用户就已经失败了。

三个立场：第一，云端 API 必须是默认选项，不需要用户理解模型和推理。第二，本地模型是高级选项放在 Settings 里，标注硬件要求。第三，Prompt 工程质量决定用户留存——一致性比质量更重要。先用云端 API 做到"点一下就有图"，再通过精心设计的 Prompt 管道保证"图和文对得上"，最后才考虑本地模型。用户不应该为我们的技术选择买单。

### 恶魔

预判了 5 大思维陷阱：

1. **虚假二分法**——"要么 API 要么本地"。正确的架构从来不是二选一，而是抽象出统一的图片生成接口。
2. **幸存者偏差**——"我本地跑出来的图效果很好"。通常是手握 RTX 4090、调了三天、挑了十张里最好的一张。在没有量化评估指标之前，这些断言一文不值。
3. **未经验证的核心假设**——"文本到图像的 Prompt 转换很简单"。小说文本充满隐喻。"他眼底闪过一丝不易察觉的悲伤"——这个怎么画？这是语义鸿沟，大多数人根本意识不到。
4. **成本盲区**——只算 API 费用，不算显卡、调试、版本跟踪、质量筛选、一致性迭代的隐性成本。
5. **功能蔓延**——"加上 ControlNet、IP-Adapter 就能保证一致性"。等你把这条链路搭完，写的已经不是小说配图模块了，是一个完整的 AI 图像生产流水线。

### 苏格拉底

提出 4 个核心追问：

1. "小说内容"究竟是什么？章节的情节摘要？高潮瞬间的场景描写？还是角色外貌段落？三者需要的图像生成策略完全不同。
2. "一致性"是对谁而言的？对作者脑海中的形象？对读者阅读时自行构建的形象？还是前后两章之间的形象？这三种"一致"可能互相矛盾。
3. 把小说文本发送给 LLM 生成大纲和章节时，隐私风险是否已经存在了？为什么到生成图片这一步才开始担忧？
4. 一张由 AI 生成的图片，放在读者面前的那一刻，它是在帮助读者想象，还是在替代读者想象？

## 第二轮：激烈交锋

### 架构师

强烈反对编程手"不要试图抽象出统一接口"。这个观点的本质是"因为现在难，所以不做"。但差异恰恰是抽象层存在的理由——抽象的不是响应结构，而是能力契约。`ImageProvider` trait 只需要三个方法：`generate(prompt) -> ImageResult`、`health_check() -> bool`、`estimate_cost(prompt) -> Cost`。

被体验者说服了一点：默认路径必须是零配置的。调整立场：抽象层必须存在，但第一版只实现一个 `ApiProvider`，接口设计预留本地实现的扩展点，不急着写本地适配器。

新论点：角色视觉一致性不能靠 Prompt 工程解决。DALL-E 对每次生成都是独立的，没有跨会话记忆。必须在架构层引入"角色视觉档案"——为每个角色预生成参考图，后续生成时作为约束输入。

### 设计师

强烈不同意编程手"先做 API 链路再说"。这不是工程优先级问题，是**审美债务**问题。先跑通 DALL-E，用户就会习惯"AI 配图就是这种割裂感"，回头想引入风格一致性时就是推翻用户已有的视觉体验。

坚持立场但做调整：不是要求一步到位实现 ImageProvider trait，而是要求**第一步就建立视觉风格锚点**。生成第一张图之前，先推导出"本书视觉规范"——色调、画幅比、渲染风格关键词——持久化到 `visual_profile.yaml`，后续所有出图调用都注入这个约束。

回应苏格拉底的问题：配图应该画文字没写到的东西。角色的心理状态用色调暗示，但角色具体面孔不该被钉死。视觉语义翻译层的核心职责是"提取叙事情绪，生成氛围图"。

### 编程手

强烈不同意设计师关于"本地 LoRA 微调"的定位。LoRA 微调需要训练数据集（几十张风格统一的参考图），用户是写小说的不是画师。本地跑 LoRA 至少需要 8GB 以上显存的 GPU，和体验者说的"零配置"直接矛盾。

对 ImageProvider trait 做让步：trait 本身不贵，定义一个接口几行代码的事。但反对在第一版就做"角色视觉档案系统"。先解决一个具体场景——比如从角色卡片生成一张配图——端到端跑通，再谈抽象。

新论据：项目 Rust 后端 AI 模块已有 OpenAI 兼容客户端和 Ollama 客户端双轨实现。最务实的路径是把图片生成复用现有的 AI 客户端基础设施，OpenAI 格式对接 DALL-E / SD API，Ollama 对接本地自动生图模型。不需要新架构，只需要在现有 `ai.rs` 上扩展 `generate_image` 方法。

### 体验者

强烈不同意编程手的"先做 API 路线，不要过早抽象"。这个项目是桌面应用，用户选择 Tauri 很大程度上是因为隐私和离线需求。如果第一版就把"联网调 API"作为唯一路径，等于把一半目标用户挡在门外。API key 配置是付费墙，用户还没看到一张配图就被要求填 key。

修正立场为：**可预期的质量比偶然的高质量更重要**。用户能接受风格统一的简笔画，但无法接受第一张水墨、第二张赛博朋克。一致性的真正含义是**风格锁定**。

新论据：项目 Settings 页面已有多 Provider 切换机制，图片生成完全可以复用这套心智模型。如果默认提供免费/低成本的云端选项，就能实现"零配置首次体验"。最后建议配图应该是**可隐藏的**——用户生成后可以一键折叠所有配图回到纯文字阅读。

### 恶魔

猎杀开始：

编程手说"先跑通 DALL-E 链路"——但没说**哪个** API。DALL-E 3 一张 0.04 美元，Flux 通过 Replicate 一张 0.003 美元，SD WebUI 本地免费。延迟从 3 秒到 60 秒不等。连成本和延迟都没量化，跑通什么？

架构师的 `ImageProvider` trait 就是功能蔓延的活标本。小说应用的核心是文字创作，他却要建"角色视觉档案系统"和"风格模板系统"——这是在造 Midjourney 竞品吗？

设计师说"本地 LoRA 微调定制风格"。用户群体是小说作者，他们有多少人有能力训练 LoRA？这句话对 99% 的用户来说是废纸。"用户必须确认角色参考图"——那零配置的体验从哪来？

体验者说"一致性比质量重要"。凭什么是二选一？一张风格统一的烂图和一张精美的但角色鼻子不一样的图，用户都不满意。这就是第一轮警告的虚假二分法。

### 苏格拉底

追问架构师：你说"本地只支持固定几套预设工作流，不做自定义编排"。但如果用户恰好是已经在用 ComfyUI 画画的设计师，她会接受被锁死在预设路径里吗？你所说的"不做自定义"，究竟是在简化系统，还是在简化你对用户的想象？

追问编程手：你说"先跑通 API 链路，不要过早抽象"。但这个应用已有 Provider 枚举和双 AI 后端切换。当接入第二个、第三个图片 API 时，你打算在 commands.rs 里堆 if-else 吗？现有的 Provider 模式本身，是过早抽象还是刚刚好？

追问体验者：你说"默认体验必须零配置"。但零配置意味着替用户选一个图片 API 并预填 key——这做得到吗？如果做不到，"零配置"和"必须配置"之间的中间态究竟长什么样？

## 第三轮：最终辩护

### 架构师

抽象时机：坚持定义 trait，但只实现一个 Provider。接口定义的成本是零——一个 Rust trait 五行代码，换来后续扩展不需要改业务逻辑。

优先路线：API 零配置先行，本地做第二版。先验证"文本→Prompt→图片"这条管线是否值钱，如果用户根本不看配图，本地方案就是 wasted effort。

一致性：视觉风格锚点，不做角色档案。设计师的 `visual_profile.yaml` 是对的——给"这本书"定调性。一个 YAML 文件存风格关键词、色彩倾向、构图偏好。

配图本质：氛围，不是面孔。当前技术用文字描述生成一致的角色面孔，成本极高、可靠性极低。氛围图才是文生图擅长的。

**Actionable 建议：**
- Phase 1：ImageProvider trait（5 行）+ ApiProvider 实现；visual_profile.yaml 生成；文本→Prompt 转换引擎；配图作为可隐藏的章节装饰
- Phase 2：LocalProvider；角色视觉档案；批量生成

### 设计师

四个争议点全部让步或调整：

抽象时机——让步，先跑通。但 prompt 构建逻辑必须集中在一个模块里。优先路线——让步，API 先行。但 API 调用必须封装在 trait 后面，接口定义留好扩展位。

一致性——坚持视觉风格锚点，但简化为：用户选一个风格关键词（"水墨""赛博朋克""油画"），作为 system prompt 前缀注入每次图片生成请求。一个字段，零摩擦。

配图本质——坚持画氛围不画脸。实操建议：提取每章的情感标签（复用现有 context.md 意图层的 emotional_arc 字段），直接喂给图片生成器作为 prompt 种子。不新增任何数据结构，只复用已有信息。

### 编程手

抽象时机——折中。在 `ai.rs` 里加一个 `ImageProvider` enum（不是 trait）保持风格一致，代价十几行代码。坚持不做 trait——第一版只有一个实现，trait 是在为幽灵写代码。

优先路线——坚持 API 先行。补上量化数据：OpenAI 兼容的图像 API（硅基流动、Replicate）单张成本约 0.01-0.05 美元，延迟 5-15 秒。LoRA 需要至少 20 张标注数据 + 8GB+ 显存训练卡。

一致性——让步。同意在 prompt 模板里固定一个视觉风格前缀（"水墨风格，深色基调，金色点缀"），复用项目的"墨夜书房"美学。只是一个常量字符串，几乎零成本。

配图本质——氛围优先。角色面孔跨图一致性是未解决的学术问题，第一版不该碰。

**Actionable 建议：**
1. ai.rs 加 ImageProvider enum + generate_image 方法
2. config.yaml 加 image_provider / image_model 字段
3. Rust 端写 text_to_image_prompt 提示词模板
4. 前端 Chapters 页面加"生成配图"按钮
5. 验证标准：给定一段场景描写，自动生成风格统一的氛围图

### 体验者

抽象时机——让步。编程手说服了现在建 trait 成本极低，但只定义 `generate_image(prompt, style) -> Result<ImageData>` 这一个方法。

优先路线——坚持云端 API 优先，但接受本地路径并行验证。折中方案：首次启动时引导用户填一次 API Key（类似 Ollama 连接测试的现有流程），之后记住。

一致性——折中：不建角色视觉档案，在提示词模板中固定风格前缀（如"水墨风格，深色调，无文字"）。配图区域默认可折叠/可隐藏。

配图本质——氛围为主，角色为辅。建议提示词以场景氛围为主，仅在角色首次登场时尝试生成角色形象。

**Actionable 建议：** 复用现有 Settings 页面 Provider 切换机制，加"图片生成"Tab。前端章节阅读页预留图片位，默认折叠。先跑通，再迭代。

### 恶魔

**存活的论点：** 编程手的"先跑通 API，不早抽象"在实战中站得住脚。体验者的"配图可隐藏"和"零配置默认"简单、务实、无人能反驳。

**土崩瓦解的论点：** 架构师的 `ImageProvider` trait 在第二轮就已经是在给空气做接口。设计师的 LoRA 定制被正确猎杀。

**最头疼的论证：** 编程手建议复用 `ai.rs` 的 Provider 切换机制来做图片生成，天然解决配置和切换问题。

**不得不承认被说服的：** 设计师从"画角色面孔"退到"画氛围而非面孔"是被现实击打后的正确判断。当前 AI 图像生成对角色一致性的控制力确实不够。

**最终裁定：** 第一版只做 API 图片生成，氛围图优先于角色图，复用现有 Provider 机制，配图可隐藏。其余一切——trait、LoRA、视觉档案——等有人真正用到再说。

### 苏格拉底

三轮讨论，所有人都在回避一个事实：你们还没有说清楚，用户按下"生成配图"按钮之后，系统究竟要拿什么去画。NovelData 里有标题、类型、主题，章节正文是 Markdown，context.md 里是三层记忆，但没有一行数据描述过"这一章应该出现什么画面"。

**终极问题一：** 在你们的系统里，谁负责把一段 3000 字的小说文本翻译成一张图片的 prompt？是 Rust 后端用 AI 再调一次文本生成？是前端硬编码规则？还是用户自己写？这个翻译的质量天花板，你们打算定在哪里——"能看"还是"认得出是同一部小说"？

**终极问题二：** 如果文本到图片 prompt 的翻译本身就需要一次 AI 调用，那整个功能的本质就不是一个"图片模块"——而是一个新的 AI 编排流程，和 create_novel 平级。你们是在给现有的 app 加一个按钮，还是在造一个新产品？这个答案决定今天是该写一个 `image.rs` 还是该重新审视整个架构。

## 主持人总结

### 共识点

- **API 先行**：第一版以云端 API 为主，本地部署留作第二版。所有角色（包括最初主张本地优先的设计师）最终都接受了这一点。
- **氛围图优先于角色图**：当前 AI 图像生成技术无法可靠地保证角色面孔一致性，配图应以场景氛围、情绪色调为主。设计师的主动退让获得了全员认可。
- **复用现有架构**：在 `ai.rs` 基础上扩展图片生成能力（enum 或 minimal trait），复用现有的 Provider 切换机制和配置管理。
- **配图可隐藏**：用户体验上，配图默认折叠/可关闭，不打断纯文字阅读体验。
- **风格一致性通过 Prompt 模板实现**：不建重量的角色视觉档案系统，而是在 prompt 模板中注入风格前缀（与"墨夜书房"美学一致），成本低、效果可验证。

### 分歧点

- **抽象形式**：架构师主张 trait（接口定义），编程手主张 enum（枚举变体）。本质差异在于：trait 预设了多实现的未来，enum 则是"现在只有一种实现，用枚举区分类型"。这个分歧不影响第一版交付，可在实现时根据 Rust 社区惯例决定。
- **文本→Prompt 翻译的实现归属**：苏格拉底的终极问题未被充分回答——这个翻译是作为一个新的 AI 编排流程（与 create_novel 平级），还是作为 image 模块的内部步骤？这个决策影响整体架构复杂度。
- **零配置的实现方式**：体验者坚持"零配置"，但开源桌面应用无法内嵌 API Key。首次引导填写 vs 集成免费额度 vs 提供多平台选择，具体方案尚未确定。
